# Vardiel v0.1 scope and acceptance criteria

## Release objective

Vardiel v0.1 is a local, evidence-driven Linux operations diagnostic agent. It must be useful for daily host, systemd, Docker, and web-service troubleshooting while remaining bounded, inspectable, and read-only.

The release is also the intended implementation baseline for the intelligent-agent course project, but engineering decisions must serve the long-term product rather than only the report.

## Primary user stories

### Host resource pressure

As an operator, I can ask why a Linux host feels slow. Vardiel gathers bounded host evidence, applies deterministic analyzers, and returns a report that distinguishes observations, findings, hypotheses, uncertainty, and next steps.

### systemd service unavailable

As an operator, I can identify why a named systemd service is unavailable. Vardiel validates the unit name, inspects service state, failed units, listeners, and relevant host pressure without executing a restart or arbitrary command.

### Web endpoint unreachable

As an operator, I can diagnose a failed web endpoint across DNS, HTTP, TLS, local listeners, systemd, and Docker evidence. Vardiel presents an evidence chain instead of guessing from one probe.

## Required public concepts

### DiagnosticCase

Represents one investigation and contains stable identity, timestamps, user goal, status, selected playbook, and report references.

### DiagnosticPlan

A validated, versioned, read-only execution plan containing bounded steps and explicit dependencies.

### Observation

A normalized record produced by one tool execution. It distinguishes execution status from the health assessment of the observed target.

Minimum fields:

```text
id
case_id
step_id
tool_name
observed_at
execution_status
assessment
summary
facts
warnings
sensitivity
```

### Finding

A deterministic analyzer result that cites one or more observation IDs.

Minimum fields:

```text
id
severity
category
title
summary
evidence_ids
confidence
```

### DiagnosisReport

The default user-facing output. It contains the conclusion, observed evidence, deterministic findings, hypotheses, uncertainty, next steps, and optional action proposals.

The report must not contain raw prompts, complete message histories, secrets, raw infrastructure error bodies, or unbounded tool output.

### ActionProposal

A non-executable recommendation for a possible state change. In v0.1, `execution_supported` is always false.

## Required CLI surface

The target CLI surface is:

```text
vardiel diagnose [--playbook ID] PROMPT
vardiel case list
vardiel case show CASE_ID
vardiel case export CASE_ID --format json|markdown
vardiel playbook list
vardiel tool list
vardiel tool run TOOL [JSON]
vardiel doctor
vardiel mcp stdio
vardiel version
```

CLI stdout must remain machine-readable for commands that return data. Progress and diagnostics belong on stderr.

The default `diagnose` output is a sanitized `DiagnosisReport`, not the complete Agent message history.

## Required read-only host tools

The exact final names may be refined in the Tool Contract task, but v0.1 must include equivalent capabilities:

```text
host_inventory
host_load_snapshot
host_memory_snapshot
host_pressure_snapshot
host_filesystem_usage
host_process_hotspots
systemd_failed_units
systemd_unit_status
host_listeners
```

Tool requirements:

- strict JSON input decoding
- semantic argument validation
- truthful input and output schemas
- truthful read-only/idempotent/destructive/open-world annotations
- explicit sensitivity and cost metadata
- bounded execution time
- bounded response bytes and item counts
- deterministic ordering
- safe public errors
- no arbitrary shell
- no process environment output
- no complete process command line output
- no raw Journal or application logs in v0.1

## Required deterministic analyzers

At minimum:

```text
HostLoadAnalyzer
MemoryPressureAnalyzer
FilesystemPressureAnalyzer
ProcessHotspotAnalyzer
SystemdUnitAnalyzer
DockerContainerAnalyzer
WebEndpointAnalyzer
```

Existing Kubernetes and Prometheus projections may also feed analyzers when configured.

Analyzer requirements:

- no model call is required to produce findings
- thresholds come from validated configuration
- every finding cites evidence IDs
- deterministic ordering and stable fixture output
- missing evidence produces `unknown`, not fabricated conclusions

## Required built-in playbooks

### host-resource-pressure

Expected evidence path:

```text
inventory
-> load
-> memory and swap
-> PSI when available
-> filesystem and inode usage
-> bounded process hotspots
-> deterministic findings
```

### systemd-service-unavailable

Expected evidence path:

```text
validated unit status
-> failed units
-> listeners
-> host pressure
-> relevant bounded network probes
-> deterministic findings
```

### web-endpoint-unreachable

Expected evidence path:

```text
DNS
-> HTTP HEAD
-> TLS inspection
-> local listeners when applicable
-> systemd or Docker evidence
-> deterministic findings
```

Playbook requirements:

- versioned typed schema
- validated tool references
- acyclic dependencies
- per-step and total budgets
- read-only tools only
- partial-result preservation
- duplicate-call prevention
- end-to-end fixtures

## Case bundle

Default location:

```text
~/.local/share/vardiel/cases/<case-id>/
```

Expected structure:

```text
case.json
plan.json
observations/E1.json
observations/E2.json
findings.json
report.json
report.md
events.jsonl
```

Requirements:

- use atomic writes
- use restrictive permissions where supported
- reject unsafe case IDs and path traversal
- include schema versions
- avoid storing raw provider responses
- avoid storing secrets and raw infrastructure error bodies
- allow future storage backends behind an interface

A database is not required for v0.1.

## Model behavior

The language model may:

- explain deterministic findings
- connect evidence into ranked hypotheses
- state uncertainty
- recommend additional read-only checks
- draft non-executable action proposals

The language model may not:

- invent observations
- create unsupported tool names
- bypass plan validation
- execute arbitrary code or shell
- perform state-changing operations
- produce a final confirmed diagnosis without evidence references

Required providers for v0.1:

- Ark
- one OpenAI-compatible adapter, usable with a trusted local compatible endpoint

Provider SDKs remain outside `internal/agent`.

## Configuration

Configuration must support validated profiles for:

```text
model
analyzer thresholds
tool budgets
case storage
trusted infrastructure endpoints
```

Credentials are read from environment variables or bounded credential files. They are not written into repository configuration or case bundles.

## Explicit non-goals

The following are not part of v0.1:

- state-changing operations
- service or container restart
- Kubernetes writes
- arbitrary shell or script execution
- remote SSH host inventory
- Ansible execution or scheduling
- a web UI
- centralized multi-user persistence
- multi-agent orchestration
- vector retrieval or RAG
- raw log ingestion
- autonomous scheduled remediation

Astralith remains responsible for inventory, Ansible, scheduling, GitOps, web UI, and centralized approval. Kube-Sentinel remains responsible for Kubernetes controller-driven remediation.

## Release acceptance criteria

Vardiel v0.1 is acceptable only when:

1. The complete public identity is Vardiel.
2. Public errors are sanitized and stable across CLI, Agent, MCP, telemetry, and case bundles.
3. Tool Contract v2 is used by all current tools and all integration surfaces.
4. A diagnosis can run through a typed built-in playbook without a language model.
5. Findings are deterministic and reference evidence IDs.
6. A configured model can explain the same evidence without inventing tool results.
7. The three required playbooks have end-to-end fixtures.
8. Default output excludes complete message history and sensitive raw data.
9. Existing Docker, Kubernetes, Prometheus, Loki, network, SSRF, and privacy boundaries remain intact.
10. The full race-enabled test suite and build pass.
11. A clean Linux machine can follow documented installation and run at least one diagnostic scenario.
12. The release publishes versioned binaries and checksums.

## Demonstration scenarios

The release should include reproducible local fixtures or scripts for:

- a memory or filesystem pressure finding
- an inactive systemd service with a missing listener
- a web endpoint failure attributable to DNS, TLS, listener, or container state

Demonstrations must not require unsafe production changes and must clearly distinguish simulated evidence from real host evidence.
