# Vardiel v0.1 scope

## Release goal

Vardiel v0.1 proves one thing end to end: on a supported Linux host, it can
detect an allowlisted systemd service failure, perform one explicitly
pre-authorized recovery action, validate health, and close quietly or escalate
within a bounded deadline.

The release is single-host and deliberately narrow. It is the foundation for
broader host and fleet recovery, not a claim that Vardiel can already repair
most Linux incidents.

## Current status

The repository currently ships read-only CLI, Agent, MCP, network, Docker,
Kubernetes, Prometheus, and Loki diagnostics. It does not yet ship the daemon,
systemd event source, standing policy, action executor, automatic recovery, or
notification behavior described below.

## Primary scenario

An administrator enrolls one service unit and one health check in local standing
policy. When that unit enters a failed state:

1. `vardield` receives a systemd event and opens one deduplicated incident;
2. it records bounded unit state, exit classification, listener state, and the
   configured health-check result;
3. it matches the stable failure class to a versioned local knowledge entry;
4. the deterministic `systemd-service-unavailable` playbook evaluates current
   preconditions and standing authorization;
5. it invokes one fixed systemd restart operation for the configured unit;
6. it validates stable unit and health-check success;
7. on success it records a sanitized recovery summary without paging;
8. on policy denial, ambiguity, timeout, failed validation, exhausted attempts,
   or flapping it stops acting, creates an escalation record, and attempts one
   configured notification delivery.

No model, internet access, or fleet control plane is required on this known
path.

## Required runtime

### Always-on process

Add a Linux service mode with:

- deterministic configuration loading and validation;
- one process owner and explicit privilege boundary;
- cancellation, graceful shutdown, and bounded goroutine lifetimes;
- reconnect/backoff for systemd event subscriptions;
- health/readiness reporting that does not expose configuration or incidents;
- no dependency on Ark, MCP, OTLP, or remote connectivity for local recovery.

### Event intake

Use systemd D-Bus state changes as the primary failure signal. A bounded
compatibility timer may verify state when event delivery is unavailable. Do not
implement a high-frequency general polling framework.

Normalize only the fields needed to identify the configured unit and stable
failure class. Raw Journal messages, environment values, complete command
lines, coredumps, and arbitrary unit properties are not incident inputs in
v0.1.

### Incident state

Keep one typed incident per host, playbook, and target generation. Required
state includes:

```text
id
schema_version
host_id
playbook
target
state
opened_at
updated_at
deadline
attempts
reason_codes
knowledge_id
policy_decision
action_outcome
validation_outcome
escalation_reason
```

Equivalent events coalesce into the active incident. State transitions are
deterministic and crash-safe enough to prevent duplicate actions after restart.
The first persistence format may be a small local JSON/JSONL journal; v0.1 does
not require a general CaseStore interface or Markdown report bundle.

### Minimal knowledge support

Ship the systemd playbook with at least one repository-reviewed, versioned local
Markdown knowledge entry covering its stable failure classes. The entry has
bounded metadata for identifier, version, applicability, signals, likely causes,
registered observation or playbook references, validation expectations, and
source provenance.

Lookup uses deterministic scope, tag, error-code, and bounded-signature matching;
no network service, embedding model, or vector database is required. Knowledge
text is advisory and untrusted. It cannot define an executable operation or
widen policy, and diagnosis or escalation cites the matched identifier and
version. A missing or ambiguous match does not block the fixed known playbook,
but it is recorded without inventing a remedy.

## Standing policy

An administrator must configure each recoverable unit explicitly. Policy
includes at least:

- exact unit name;
- whether automatic restart is authorized;
- health-check type and bounded target;
- action timeout and total incident deadline;
- maximum attempts and cooldown;
- circuit-breaker threshold and open duration;
- optional maintenance window;
- whether the action's lack of rollback is accepted.

Unknown units, wildcard unit names, missing policy, expired policy, malformed
policy, and conflicting policy fail closed. A model, event, user prompt, or
remote response cannot add or widen authorization.

Only an administrator may change standing policy in v0.1. A multi-user API and
central policy distribution are future work.

## Fixed action

The only v0.1 mutation is a typed systemd restart for the exact configured unit.
It must use a typed systemd interface or fixed argument builder and may not
expose arbitrary `systemctl` flags, modes, unit paths, environment assignments,
or shell text.

Required action behavior:

- acquire a per-unit lock before the final policy/precondition check;
- record the observed pre-state;
- enforce context cancellation, one action timeout, and the attempt budget;
- classify the result without returning raw systemd or Journal text publicly;
- reject a second equivalent action while one is active;
- open the circuit breaker after configured repeated failures;
- never turn a failed restart into success without independent validation.

A service restart has no general semantic rollback. Policy must acknowledge that
classification. If restart or validation fails, Vardiel stops after the attempt
budget and escalates instead of inventing a reverse action.

## Validation

Recovery requires both:

- the unit remains active for the configured stabilization interval; and
- the configured bounded health check succeeds.

The health check is one existing safe local TCP or HTTP probe with a fixed target
from administrator configuration. It preserves current target validation,
timeouts, TLS verification, redirects, byte limits, and output projection.

Execution success and observed health remain separate fields.

## Quiet close and escalation

A successful routine recovery writes a sanitized local record and emits normal
telemetry but does not require a user notification.

Escalate when:

- policy does not authorize the action;
- observations are incomplete or contradictory;
- the unit or health target falls outside the configured scope;
- the deadline, attempt, or concurrency budget is exhausted;
- restart or validation fails;
- the circuit breaker opens because of flapping;
- privilege, systemd connectivity, persistence, or validation is unavailable;
- potential data loss or a security incident is indicated.

The escalation record contains stable reason codes, impact, bounded
observations, attempted actions, validation state, and the smallest requested
operator decision.

v0.1 includes one configured HTTPS webhook notifier. The endpoint is
administrator configuration, never event or model input. It requires HTTPS,
rejects URL user information, query strings, fragments, redirects, ambient
proxies, and insecure TLS, bounds payload and response bytes, reads any bearer
credential from a bounded absolute file, and emits only the sanitized escalation
contract. Delivery has its own timeout, deduplication key, and retry budget.
Delivery failure is recorded and retried independently; it never reopens the
incident or repeats a recovery action.

## Performance acceptance

On the documented supported-host fixture:

- P95 systemd failure event intake is at most 1 second;
- P95 approved restart start is at most 5 seconds after intake;
- the incident reaches verified recovery or escalation within 30 seconds;
- the known path performs zero model and remote-control-plane calls;
- event bursts for the same unit produce one active incident and no duplicate
  concurrent restart.

Tests enforce configured deadlines with deterministic fakes. Release notes must
also record measurements from a real systemd host, including hardware, kernel,
systemd version, load, sample count, and percentile calculation. CI timing alone
is insufficient evidence.

## Required tests

- normal failure -> authorized restart -> stable recovery;
- unit active but health check still failing;
- policy denied, missing, expired, malformed, and conflicting;
- invalid or wildcard unit identifiers;
- event deduplication and concurrent delivery;
- cancellation before and during action;
- action, validation, and total deadline expiry;
- restart failure and validation failure;
- attempt budget, cooldown, and circuit-breaker behavior;
- daemon reconnect and graceful shutdown;
- crash/restart without duplicate action;
- permission and unavailable-systemd failures;
- safe public errors and deterministic incident serialization;
- deterministic knowledge matching, missing/ambiguous entries, provenance, and
  prompt-injection/non-execution boundaries;
- secret, path, header, Journal-text, and prompt-injection non-leakage;
- quiet success, one escalation notification, deduplication, bounded retry, and
  notification failure without action replay;
- zero model calls on the deterministic fast path;
- real Linux systemd fixture validation documented for release.

The default unit suite remains deterministic and must not require production
infrastructure, real credentials, root, or internet access.

## Preserved current boundaries

- no arbitrary shell or model-generated code execution;
- no arbitrary unit, action, systemd method, filesystem path, or health target;
- strict input validation and deterministic outputs;
- stable sanitized public errors;
- no credentials, environment values, raw provider bodies, raw Journal text,
  coredumps, complete command lines, or private paths in model/public output;
- current SSRF, DNS re-resolution, redirect, TLS, endpoint, size, count,
  timeout, cancellation, output-projection, telemetry, CLI, and MCP boundaries;
- current Docker, Kubernetes, Prometheus, and Loki tools remain read-only;
- Kubernetes recovery remains Kube-Sentinel's responsibility.

## Explicit non-goals

- automatically recovering more than the configured systemd scenario;
- arbitrary shell, scripts, packages, files, users, firewall, routing, storage,
  reboot, shutdown, Docker, or Kubernetes mutation;
- model-generated actions or model-granted authority;
- a general Tool Contract v2 migration;
- a general evidence/case-bundle platform;
- raw Journal, application-log, coredump, or pcap ingestion;
- fleet inventory, remote SSH, Ansible, centralized scheduling, or web UI;
- notification providers beyond the one configured HTTPS webhook;
- multi-user policy administration;
- remote or semantic RAG, vector databases, multi-agent orchestration, or extra
  model providers.

## Release acceptance criteria

Vardiel v0.1 is acceptable only when:

1. a clean supported Linux host can install and run `vardield`;
2. one exact configured service failure completes the primary scenario;
3. known recovery stays inside the performance budgets without a model;
4. unauthorized, repeated, ambiguous, and failed recovery paths stop safely;
5. action and validation outcomes are distinct and auditable;
6. the diagnosis cites the matched knowledge entry and knowledge content cannot
   add an action or widen authorization;
7. successful routine recovery remains quiet, while an unresolved fixture sends
   one sanitized notification without action replay;
8. secrets, raw logs, private paths, and raw errors do not cross public,
   notification, or telemetry boundaries;
9. existing read-only tools and security/privacy tests remain green;
10. deterministic tests pass with the race detector;
11. a real-host fixture records exact recovery timing and environment;
12. binaries, checksums, install, upgrade, rollback, and removal instructions
    are published.
